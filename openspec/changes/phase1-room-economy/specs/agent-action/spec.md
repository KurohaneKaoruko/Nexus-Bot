# Spec Delta

## Purpose

Agent 把已分配任务转为本 Tick 行动提案，ActionBroker 统一校验、仲裁并提交到游戏 API——行动控制单点化，杜绝分散的原生调用。

## ADDED Requirements

### Requirement: 提案与提交分离
行动必须两段式执行：提案阶段只登记计划（不触碰游戏 API），提交阶段统一按管线排序、校验并调用原生 API；提交后每单位每管线的最终结果可查询。

#### Scenario: 提交后可查结果
- **WHEN** 提交阶段完成
- **THEN** 每个已提交计划都有带返回码与分类的结果记录，可按单位查询

### Requirement: 行动前校验
提交前必须按行动种类校验：执行者存活且非 spawning、任务租约归属该执行者、目标 ID 可解析且类型匹配、身体部件/资源量/目标容量满足、近距离动作已在其范围内；任一不满足则不产生该原生调用。

#### Scenario: 不在范围改走移动
- **WHEN** 工作类动作的目标超出作用距离
- **THEN** 本 Tick 产生移动计划而非重复提交注定失败的作业调用

#### Scenario: 目标不可解析
- **WHEN** 计划引用的目标 ID 无法解析到对象
- **THEN** 结果分类为 replan，关联任务被标记失败原因并进入回收

### Requirement: 行动管线仲裁
同 Tick 冲突必须按官方行动管线规则处理：同一执行者同一管线只提交优先级最高的计划（其余被抑制并记录），不同管线可并行提交；不得引入"每单位每 Tick 只许一个动作"的错误限制。

#### Scenario: 同管线冲突择优
- **WHEN** 同一 Creep 同 Tick 产生两个同管线计划（如两次 work）
- **THEN** 仅优先级较高者提交，另一条被抑制并计数

#### Scenario: 跨管线并行
- **WHEN** 同一 Creep 同 Tick 产生移动与作业两个不同管线计划
- **THEN** 两者都被校验提交，互不抑制

### Requirement: 返回码分流
提交结果必须按原生返回码分类处置：成功为 accepted；可恢复码（如不在范围、疲劳）为 retryable 并关联下 Tick 计划；需要重规划（目标失效、容量已满）为 replan 并反馈任务系统；参数/状态非法为 invalid 并限频告警。同一失败的重复发生必须可观测，防止循环刷错。

#### Scenario: 可恢复码重试
- **WHEN** 原生返回 ERR_NOT_IN_RANGE 且计划已附带移动
- **THEN** 结果分类为 retryable，任务保持租约

#### Scenario: 循环失败可见
- **WHEN** 同一单位同一行动连续多次失败
- **THEN** 失败计数进入遥测，达到阈值后任务进入失败流程而非无限重试

### Requirement: 唯一执行入口
除感知、Memory 迁移与纯计算外，任何模块不得绕过提交阶段直接调用 Creep/Room 的原生行动 API；原生调用只允许出现在统一提交路径中。

#### Scenario: 提交外无原生调用
- **WHEN** 审查一个 Tick 的执行过程
- **THEN** 全部原生行动调用都发生在提交阶段，任务/分配/感知阶段零调用
