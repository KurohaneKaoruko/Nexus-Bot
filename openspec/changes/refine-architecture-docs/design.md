# Design

## Context

四篇文档现状（2026-10-17 落库，commit 16f7d0f）：01 篇 34 章 / 02 篇 38 章 / 03 篇 42 章 / 04 合并版 39 章约 2500 行。结构完整但为审计快照风格：核心抽象（ActionResult、ResourceLedger、Memory schema、层间接口）只有原则句，Phase 章节无进入条件/验收门禁/回滚策略三要素，03 篇 35 项 BUG 无处置状态标注。同时并行变 `nexus-architecture-refactor`（58/61 tasks）正以四篇文档为依据实施 Phase 0–15，文档深化会直接影响其剩余任务口径。03 篇 §41 的 Bug 管理方法与 AGENTS.md 缺陷治理规则（先修 bug、docs/bugs 勾销制）存在双口径。04 合并版与前三篇内容重叠约 80%。

约束（来自项目准则与既定决策）：

- 文档即设计权威：整体架构严格按 docs/ 设计执行；冲突以 docs 为准。
- 用户已确认两项决策：全面深化（非只补关键缺口）；04 合并版降级为索引。
- 本变更是纯文档变更，不触碰 src/、docs/bugs/ 文件本身、openspec/specs/ 主 specs。
- 与 nexus-design/ 23 篇的关系：四篇为目标架构权威源，nexus-design 为历史演进与专题设计。

## Goals / Non-Goals

**Goals:**

- 四篇文档从"审计快照"升级为"可执行规范"：字段级定义、状态机、验收门禁、度量方法可直接指导实现与验收。
- 消除双份维护：04 降级为索引页后，目标架构内容只在 01/02/03 维护。
- 治理口径统一：BUG 处置状态、修复顺序、缺陷管理流程在 03 篇与 docs/bugs、AGENTS.md 之间单一口径。

**Non-Goals:**

- 不修改任何 src/ 代码、docs/bugs/ 既有缺陷文件内容、openspec 主 specs。
- 不重写 nexus-design/ 23 篇（只在冲突处加废弃/改向标注）。
- 不为文档内容建立自动化 lint/CI 校验（交叉引用规范先靠约定与评审）。
- 不调整并行变更 nexus-architecture-refactor 的既有 artifacts（深化后如有口径出入，由其实施侧吸收）。

## Decisions

### D1：深化采用"章节就地扩写"，不拆分新文件

01/02/03 保持单文件与既有章节号体系，深化内容写进对应章节内部（新增小节或表格）。
**理由**：项目文档习惯为长文分章（nexus-design 同风格）；拆分文件会打断既有引用（并行变更 artifacts、git history、AGENTS.md 中的"docs/nexus-design/21"式引用模式）。
**替代方案**：按主题拆成子文档目录树——被否，引用维护成本高于收益，且与"避免复杂化"准则冲突。

### D2：01 篇深化以"契约表"为主形态

ActionResult 五分类、ResourceLedger 五态、Memory schema、层间接口均用统一形态表达：类型定义（TS interface 风格）+ 字段表（字段/类型/生命周期/约束）+ 转换/判定表（时点或条件矩阵）+ 不变量清单。
**理由**：文档读者是实施者与后续 agent；契约表可直接照抄为代码类型与测试断言，比散文描述更防歧义。
**替代方案**：Mermaid 状态图为主——作为辅助保留（五态转换、Ownership 三阶段用图），但字段与判定以表为准。

### D3：02 篇每个 Phase 章节统一补"三要素块"

结构固定为：`进入条件`（依赖哪些前置 Phase 产出 + 现存代码基线）→ `验收门禁`（编号门禁项，每项含指标与度量方法）→ `回滚策略`（开关/还原步骤）。Phase 0 另附基线指标采集方法表。
**理由**：固定结构让"Phase 完成"可审计（对应 spec 场景"验收可客观判定"）；门禁项编号后可直接被 tasks 与 commit message 引用。
**替代方案**：自由格式逐 Phase 定制——被否，38 个 Phase 章节风格会再度漂移。

### D4：03 篇对账采用"状态标注 + 映射表"，不搬运 docs/bugs 内容

35 项 BUG 各加一行状态标注（已修复 / 已登记 docs/bugs / 仍在代码 / 已失效），篇末新增映射表（BUG 编号 ↔ docs/bugs 文件 ↔ 优先级）。§37–39 修复顺序章节改写为指向 docs/bugs 优先级体系的汇总视图。
**理由**：docs/bugs 是缺陷唯一事实源（AGENTS.md 明确）；03 篇只做存量审计结论的对账快照，避免第二份缺陷内容。已失效判定依据：代码重构后问题对象不存在（如 legacy 移除后其 BUG 自然失效）。
**替代方案**：03 篇逐项展开修复细节——被否，与 docs/bugs 重复且违反单一事实源。

### D5：04 索引页保留"执行摘要 + 层级说明 + 章节索引表"

04 重写后含：① 执行摘要（保留现有 §1 核心判断，压缩至一屏内）；② 文档层级说明（四篇 vs nexus-design 的权威关系）；③ 主题 → 篇·章节号索引表（架构主题为行，01/02/03 章节　为列）；④ docs/bugs 与 AGENTS.md 治理入口链接。
**理由**：执行摘要是四篇的"电梯陈述"，读者（含后续 agent）需要不读全文即可把握核心判断；索引表是 04 存在的唯一价值。
**替代方案**：04 整文件删除——被否，git 历史与潜在外部引用会断链，且损失摘要入口。

### D6：BUG 状态判定基准取"当前 main 分支代码实况"

03 篇状态标注以审计时点（落库日）代码为准打标，并在篇首声明基准 commit；后续状态演进只在 docs/bugs 侧勾销，03 篇不追踪（快照对账，非活文档）。
**理由**：03 篇若追踪修复状态会与 docs/bugs 形成双活记录。声明基准 commit 后，读者能明确知道快照时效。
**替代方案**：03 篇维护为活文档——被否，双活必然漂移，违背 D4 单一事实源原则。

### D7：交叉引用规范用轻量正则可查的文本格式

篇内引用格式统一为 `01 §16`、`02 §13` / 篇名（如"见 02 §13"）；nexus-design 侧冲突标注格式为 `> ⚠ 已由四篇取代：见 01 §16`（blockquote 引用行）。
**理由**：无自动化校验（Non-Goal），格式必须人眼可读、grep 可查（`grep -n "§" docs/`）。
**替代方案**：Markdown 链接 + 锚点——被否，中文标题锚点不稳定，章节号更可靠。

## Risks / Trade-offs

- [文档体量膨胀，01/02 篇可能翻倍] → 深化内容以表格与类型契约为主（信息密度高）；04 索引页承担导航，抵消检索成本。
- [03 篇快照时效衰减] → D6 基准 commit 声明 + 状态标注里"已失效"类目兜底；新缺陷一律走 docs/bugs（spec 场景已锁定）。
- [并行变更 nexus-architecture-refactor 剩余 3 任务与深化后口径出入] → 本变更 tasks 里安排核对步骤：深化完成后 diff 其 design/tasks 引用的章节号是否仍成立（章节号体系不变，仅章内扩写，预期影响极小）。
- [04 索引表随前三篇章节调整而死链] → 索引表集中在 04 单一表格内，前三篇调整章节结构时 tasks 中列为检查项；spec "索引不漂移"场景约束此点。
- [深化过程中发现文档间自相矛盾（如 01 与 02 对同一机制描述不一）] → 处理规则：以更接近运行实况的描述为准修正另一篇，并在 commit message 记录修正点；不静默取舍。

## Migration Plan

纯文档变更，无部署概念。落地顺序（tasks 据此展开）：

1. 01 篇深化（ ActionResult → ResourceLedger → Memory schema → 层间接口 → Event/Telemetry/CPU）。
2. 02 篇三要素补齐（Phase 0 基线表 → 逐 Phase 三要素 → Ownership 三阶段 → Legacy 门禁）。
3. 03 篇对账（基准声明 → 35 项状态标注 → 映射表 → 修复顺序合并口径 → §41 流程统一）。
4. 04 篇重写为索引页。
5. 交叉引用规范化 + nexus-design 冲突标注。
6. 与 nexus-architecture-refactor artifacts 的引用核对。

回滚：文档在 git 管理下，任一篇深化不满意可单独 revert 对应 commit（各篇独立 commit）。
