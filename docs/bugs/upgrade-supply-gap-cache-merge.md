# 缺陷: 建筑缓存正确化暴露升级供能断点 (无 cc 时升级工断粮)

> 发现: 2026-10-15 · 优先级: **P2 (暂缓, 随增量刷新一并处理)** · 关联: P1-14 (建造吞吐停滞家族)
> 状态: 结构缓存合并已收敛为"同轮子新版内核 + 行为语义与旧版完全一致", 本缺陷不再现;
> 此处保留取证结论, 供未来引入增量刷新时一并设计。

## 背景

`src/core/structureCache.ts` 与上游同源仓库的 structureCache 轮子同源,
新版对引擎做了类型严格化重构 (游戏接口注入 / IdSet 类化 / 同 tick 状态内聚)。
合并采取最小口径: **只换内核实现, 保持旧版全部行为语义与本地改动**——
惰性建索引、新建筑需 room.update() 才可见、含 foreign 结构的过滤口径、
mass_stores 走引擎原生 storage/terminal、update('mineral'/'mass_stores') 的旧口径。

曾尝试顺带引入轮子入口的增量刷新编排 (工地建成/RCL 变化/失视/500t 校对自动刷),
sim `remote-mine` (30000t) 随即回归 (✗→RCL2 降级), 已回退。取证如下, 留档备查。

## 当时回归的根因 (tick 级取证)

1. **两版本下主房建造都停滞** (存量 P1-14 家族问题): t=12000 时 5 个容器工地进度仅
   ~6100/25000, 控制器缓冲容器 (cc) 全程未建成 (30000t 内两版本一致)。
2. **基线的升级供能是旧缓存"新建筑不可见"的意外红利**: 旧索引对建成后的新容器不可见 →
   远程搬运工 (`economy/roles/carrier.ts` 的 outCarry) 在老家找不到容器投点, 灌满出生线后走
   `dropCarriedAtFallback` 把余能**倒在控制器旁** (drop 意图 55 次) → 升级工按
   "cc 空则拾取工位旁落地" 捡堆续命 (upgradeController 133 次, prog 72→135 持续爬升)。
3. **增量刷新使该暗线断路**: 搬运工能看见源旁容器 → 余能改道进容器 (drop 0 次);
   cc 仍未建成 → agentSystem 的 C2 溢流落堆闸 (要求 cc 在位) 不生效 →
   **能量进得了容器、出不了到升级圈** → 升级归零 → 20000t 降级计时到点。

即: 暴露的不是缓存错误, 而是**容器可见性正确化后真实存在的供能断点**——
"源旁容器 → 升级圈"没有搬运腿 (旧路径靠落堆意外兜住, C1/C2 供线又都以 cc 存在为前提)。

## 引入增量刷新时的前置修复 (验证标准)

- 先补"源旁容器 → 升级圈"的搬运腿, 再开增量刷新; 两步可以同 PR 但供线必须先行:
  - C2 落堆闸放宽——cc 缺位时以控制器工位为落堆锚点 (复用 pileEnergyAt/hasHungryUpgrader);
  - 或 `carrier.ts` 的 `resolveCarryDepositTarget` 在无 storage 且无 cc 时,
    将"控制器旁落堆"作为与源旁容器并列的投递目的地;
- 判据: remote-mine 30000t ✓ (RCL3 维持, upgradeController 全程持续 > 0 密度,
  不再依赖 drop 兜底); boot / sprint 不回归; noErrors 全绿。

## 影响面备注

- 当前合并 (行为保真版) 已验证: typecheck 0 错、boot ✓ (L2@554)、remote-mine ✓ (RCL3 维持)、
  sprint 与纯基线逐位一致 (L2@1479, 存量失败)、CPU P95 持平;
- 旧实现"room.update() 无调用方"导致新建筑永不可见的缺陷仍原样保留——
  这是上面暗线成立的前提, 引入增量刷新时一并消除。
