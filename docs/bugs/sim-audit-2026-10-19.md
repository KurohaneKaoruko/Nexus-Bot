# sim 审计 2026-10-19: 挂钟 CPU 预算导致的运行不可复现

- **优先级: P1 (方法论级)** —— 影响 A/B 结论可信度; 触发条件明确 (机器重载)。
  已核实: 干净机上同 bundle 双跑**逐位一致** (probe-r2 ≡ probe-p1a: 采集 535024 /
  升级 58978 / 孵化 73500 / L2@4324 / L3@17982 / 生产 289); 重载机上复现失败
  (probe-r1: hashdown 260% CPU 抢占, 首 tick 613ms)。
- **现象**: 同一 bundle (`dist/main.js`)、同一场景 (`speedrun-probe.json`, seed 7,
  `deterministic_random: true`) 两次运行结果完全不同 —— t1 意图 2 vs 1, t1000
  存活 1 vs 6, 后续 RCL 时间线全线偏移。
- **根因**: 有两层, 都源于 CPU 读数是**挂钟时间**:
  1. sim 侧: CPU 限额按挂钟执行 (`Screeps-Simulation/src/engine/cpu.rs`:
     `tickLimit = min(500ms, max(0,bucket)+limit)`), 首 tick 动态布局求解实测
     190-220ms JS, 有负载时挂钟冲到 613ms (干净 240ms) 即触发截断/差异;
  2. 本体侧: `src/core/cpuBudget.ts` 用 `Game.cpu.getUsed()` 的余量做 P3 昂贵分析
     (`bucket >= LOW_BUCKET && remaining > reserve + estimatedCost`) 的准入 ——
     同一 bundle 在慢机上少做分析、快机上多做, 行为路径直接分叉。
  诱因实例: 遗留进程 `Screeps-Simulation/target/release/hashdown` 以 260% CPU
  抢占 8 分钟 (本次已清理)。
- **验证标准**: 同 bundle 连跑两次, CSV 全列 (intents/creeps/progress/eav) 逐位一致;
  跑前 `uptime` load < 1.5 且 `ps` 无 screeps 系遗留进程。
- **规避做法**:
  1. 跑前检查 load 与遗留进程 (hashdown / 泄漏的 screeps-sim), 禁止并行跑 sim;
  2. 任何 A/B 先做「同 bundle 双跑一致」自检, 再对比不同 bundle;
  3. 每次核对 CSV 首行 cpu 列 ≤ 300ms (干净基线口径 240ms) 与报告 CPU 均值
     (基线 3.57ms); 异常即作废重跑;
  4. 报告尾行「超限 tick 0」**不足以**判定有效 (r1 超限 0 但已分叉)。
- **关联风险 (线上)**: 首 tick 布局求解 190ms 是单点大头 (见
  room-observation-growth-audit)。真实服务器 CPU 上限若按 20ms/tick 口径, 落地
  首 tick 即超 9 倍预算, 会吃掉 bucket 甚至被官方语义截断 —— 上线前需评估
  (抖开求解 / 分帧 / 预计算缓存)。
