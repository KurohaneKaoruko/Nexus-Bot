### ✅ P0-16 孵化期 memory 清理竞态 (ClearModule × 引擎快照时序)【已修复 2026-10-17, nexus-architecture-refactor 任务 4.1】

- **现象**: t0/t100/t200… (100t 对齐) 孵化的 creep 出生即丢 `memory.unit`/unitCode,
  角色错轨、visuals 反复熔断、courier 对孵化件反复提交无效计划。
- **根因**: `ClearModule.end` (src/core/store/clear.ts) 每 100t 清理 `Game.creeps` 中
  不存在的 creep memory; 而引擎语义 (sim 与官服一致): spawnCreep 意图当 tick 执行后,
  creep 对象**下一 tick** 才进 Game.creeps 快照。清理窗口与孵化期完全重叠——
  正在孵化的 creep 的 memory 同 tick 被判为孤儿删除。
- **证据** (TEMP sim-probe): probe7 实证 t0 孵化单 memory `change to MISSING`;
  mini2.bot.js 实证 t0 `inGameCreeps=false`。官服孵化期同样不在 Game.creeps, 真机同病。
- **级联** (三条, 各自独立成害):
  1. **P0-16a 角色普查双轨**: 普查先走 memory.unit, 丢失后兜底 H/C/U/S 名称前缀解析;
     harvester/carrier 等非代号命名的 creep 丢失后走 legacy `exec()` 而非任务板
     (agentSystem.ts NEXUS_TASK_DRIVEN_CODES 分水岭), 行为退化不可观测。
  2. **P0-16b visuals 熔断**: roomVisuals.ts:34 发现孵化中无 unit → 调
     `spawn.spawning.cancel()`。sim 未实现该 API, visuals 模块反复熔断;
     **官服有此 API, 会真取消合法孵化单, 更危险**。
  3. **P0-16c courier 无效计划**: rush-courier 对 spawning creep 提交 withdraw 计划 →
     `warn.broker.invalid.withdraw actor-missing-or-spawning` ×16。
- **修复方向**: 清理逻辑排除孵化中名单 (`Game.spawns` 遍历 `spawning.name` 白名单),
  或清理延后一 tick 宽限; visuals 对无 unit 孵化单只告警不 cancel (至少 sim 安全);
  courier 提交前过滤 spawning。
- **修复落地 (2026-10-17)**:
  - a: clear.ts memoryClear 增 `Game.spawns[].spawning.name` 白名单 + `Memory.Nexus.units`
    名册第二道白名单——探针实证 sim shim 当 tick 写 `Memory.creeps` 而 spawning
    上快照晚一 tick, `%100==0` 清理与受理窗口重叠 (4 个孤儿窗口 t1/t101/t501/t2201
    全部起始 `%100+1`); roster 白名单后 spawn-orphan 告警 44→0;
  - b: roomVisuals drawSpawnInfo 对无 unit 孵化单改纯限频告警 (可观测层不突变, api/17);
  - c: agentSystem runAgents 对 `creep.spawning` 单位整层跳过 (courier/任务驱动/exec 全部不产出)。
- **验证 (2026-10-17, sim boot+speedrun -v)**: `actor-missing-or-spawning` 0 次 (原 ×16);
  `broker.invalid` 0 次; memory MISSING 0 次; `visuals.spawn-orphan` 0 次 (探针修复前 44);
  speedrun noErrors 绿 (错误 tick 0)。
- **复现**: `$env:SCREEPS_SIM_BIN = ..\Screeps-Simulation\target\release\screeps-sim.exe;

### ✅ P1-17 expansion 邻房候选半球硬编码【已修复 2026-10-17, nexus-architecture-refactor 任务 4.2】

- **现象**: speedrun 场景 t24300 切 expand 姿态后永无下文, 零扩张意图。
- **根因**: src/modules/strategy/expansion.ts `findExpandTarget` 用
  `E${x}N${y±1}` / `E${x±1}N${y}` 硬编码生成候选——只算东/北半球邻房。
  W5N8 算出 E5N9/E6N8 等, 与真实邻房 W4N7..W6N9 全不匹配 (remoteMining.ts
  `neighborRooms` 已有正确的世界坐标镜像换算, 未复用)。
  且 `canExpand` 要求 `Game.gcl.level > 房数`, sim GCL 恒 1 → 门槛永假, 双重死锁。
- **修复方向**: 复用 `neighborRooms` 的 E/W 镜像换算; sim 场景的 GCL 断言按
  场景实际 GCL 配置评估 (引擎侧或代码口径二选一, 避免静默短路)。
- **修复落地 (2026-10-17)**: 邻房换算抽公共 `utils/roomCoord` (roomWorldCoord/
  roomNameFromWorld/neighborRooms/orthogonalNeighbors), remoteMining 改引用,
  expansion findExpandTarget 改用 orthogonalNeighbors (E/W 镜像正确);
  canExpand 否决时输出 `expansion.veto gcl-exhausted (gcl=N rooms=M)` 限频日志 (1kt 一次)。
- **验证 (2026-10-17, sim speedrun 引擎直跑 --verbose)**: expand 姿态激活后
  `expansion.veto` 明确输出 6 次 (t25836..t30836, 每 1kt 限频一次), 不再静默;
  RCL 时间线 L2@991/L3@25835 与基线一致; boot/race-body-audit/remote-mine 全绿。
- **验证标准**: speedrun 场景 expand 姿态激活后 1000t 内出现对真实邻房的
  claim/扩张意图 (或明确的 GCL 不足日志, 不再静默)。

### ✅ P1-18 外矿链路静默 (scout 孵化饥饿)【已修复 2026-10-17, nexus-architecture-refactor 任务 4.3】

- **现象**: remote-mine 场景 (W5N8 RCL3 开局, main 档 manual, 预置
  remoteTargets=['W5N9','W4N8']) 31k tick 零跨房采集意图, scout t25659 才首现——
  场景 85% 进度处。speedrun (rush auto 档) 同样静默。
- **实修取证** (TEMP sim-probe, 六个串联断点, 逐个击破):
  1. **断点① 孵化饥饿**: `standingPriorityByRole.scout=96` 是死配置——
     `ECONOMY_ROLES` Set (bodyFactory.ts) 缺 "scout", standing 循环的
     `isSpawnUnit` 门直接跳过, scout 只能从任务路径拿 55。修复: Set 补 scout
     (类型联合里本就有, 运行时集合漏抄)。首孵 t25659 → **t18**。
  2. **断点② 规划器崩溃** (顺手修): `visited is not defined` 每 500t 崩——
     9fa3381 域拆分时 rosBlock.ts 的 import 列表漏 `visited` (旧单体同文件声明,
     拆分只搬了部分; @ts-nocheck 掩盖)。修复: 补 import。布局计算恢复真实运行。
  3. **断点③ 工地意图滞留**: Planner (commit) 注册序在 Broker (commit) 之后,
     submitIntent 的 createSite 意图本 tick 无人消费, 下 tick 被 tick 校验清空
     —— 30k tick 放量全落空 (修复②后暴露: 每 tick 重试 12 个死循环)。
     修复: 五个变体 main 的注册序 Planner 提到 Broker 前。
  4. **断点④ 分配层跨房失明**: perception 只观察 `controller.my` 房, 外矿爬
     (W4N8/W5N9) 不进 world.rooms → 不进 allocator profiles 也不被 agentSystem
     驱动——到达外矿即失联 idle。修复: WorldView 增 `remoteUnits` (可见非己方房
     己方单位摘要), Tasks profiles 与 agentSystem 驱动循环并入, aliveNames 同步
     (死亡发现/对账口径)。
  5. **断点⑤ 任务误杀**: economy planners 的 subject-gone 清扫扫
     `kinds=harvest` 全量——remoteMining 产出的远程任务 (目标房≠本矿) 不在其
     expected 口径, 每 tick 被误 cancel (claim→cancelled 振荡, 探针 t6053 实锤)。
     修复: 清扫跳过远程任务 (归 remoteMining 自管)。
  6. **断点⑥ 卸货罚站**: runRemoteHarvest 满载回本矿分支直接 submit transfer,
     距离不够每 tick ERR_NOT_IN_RANGE (carry 管线只归 retryable 不走近)——
     爬满载罚站边界 (49,12) 12k tick。修复: 距离预判, >1 格先 move。
  另: allocator 的 travelCostOf 拿异房 targetPos 坐标按同房切比雪夫算距离
  (数学错误), 远程任务 distance 按房名坐标差折算修正; canExecute 跨房放行
  扩到 harvest (原只 claim/reserve)。
- **修复效果** (probe 实证): t25000-27500 W5N9 双源双采集体驻场采集 (E50 往复)
  + W4N8 持续在岗; 单位数 14→17; 断言全绿 (creepCount 17/rcl 3/cpu 9ms/noErrors)。
  基线三场景 (boot L2@695 / race L2@994 / remote-mine L3@0) 与基线逐位一致。
- **验证标准**: remote-mine 场景 scout 首孵 ≤ RCL3 后 1500t, 跨房 harvest 意图
  随后 500t 内出现; 30k 内 W5N9/W4N8 有远程采集收入记录。
- **复现**: `screeps-sim.CMD test sim\remote-mine.sim.ts --no-bundle-check`,
  观察跨房意图时间戳与 scout 首孵 tick。

### ✅ P1-19 upgrader 断档【已修复 2026-10-17, nexus-architecture-refactor 任务 4.4】

- **现象**: speedrun 场景 t2500–t6500 upgrader 在岗 =0, 控制器进度卡 713 约 4500t。
- **实修取证** (TEMP sim-probe, 原判「水位门死循环」不成立——speedrun cpu.limit=100
  恰命中 rush 档阈值, 水位门已被 anyRush 豁免。真实机理是三层叠加):
  1. **队头阻塞**: 升级任务 (30+kindBias+upgradeBias55≈85) 驱动的 upgrader 请求
     恒排 carrier 88 之后, 攒能等待又让队头 (carrier) 空转 spawn 槽——
     t2600-4400 探针实锤 spawning=no 长达 1500t, 池内请求在、能量锯齿 10-233。
  2. **攒能等待无归零豁免**: capacityWaitRoles 的攒能语义只豁免 harvester 全灭,
     upgrader 归零 (探针 t2750-4250=0 在岗) 与 carrier 枯竭 (恒 1 只, 单只往返
     速率撑不起孵化+换代并发) 都在等永远攒不齐的大件。
  3. **能量链供给不足**: carrier 恒 1 时 fill_spawn 有人跑但 spawn 能量始终
     <200 (最小升级体 W+C+M 价) → upgrader 请求排队头也孵不出。
- **修复** (spawnDirector.ts + config/economy.ts):
  1. 归零立即复产的地板化: `bootstrapFloorOf`——攒能等待对「在岗 ≤ 地板」的
     角色失效, urgent 通道立即按现有能量小体复产。carrier 地板 = 让位搬运保底
     数 (yieldCarrierFloor), 其余角色 0 (原 harvester 特判泛化)。
  2. upgrader 归零自举 (bootstrapUpgrade): 在岗=0 且非降级紧急时插队孵化
     (对齐 bootstrapHarvest 模式, 保级优先于攒体型)。
  3. 冲级档孵化提权传导: `rushUpgradeSpawnPriority=89`——upgradeBias 只在任务层
     +55, 孵化层 upgrader 恒 85 被 carrier 88 队头阻塞; 89 压过 carrier、不越
     worker 90 (建造扩容仍是冲级前置)。
- **修复效果** (probe): upgrader=0 连续区间 1500t/2500t → **无连续断档**
  (仅开局自举前与 t8750 换代单点); progress 单调爬升无停滞平台。
  正向外溢: boot L2@695→607, race L2@994→841, speedrun L2 提速。
- **遗留** (非本 bug 范畴): speedrun L3@31k 仍未达成——升级火力 ~0.7/t 对 45000
  进度需 60k+ tick, 是定编/体型策略问题 (P2-20 建造风暴与定编校准范畴),
  断档与停滞两项验证标准均已达标。

### ✅ P2-20 RCL3 建造风暴【已修复 2026-10-17, nexus-architecture-refactor 任务 4.5】

- **现象**: speedrun L3@24672 后「RCL3 补足」每 ~100-200t 放 1 工地共 58 次,
  sites 恒 10, worker 仅 3-4 只 → 建造吞吐不匹配, L4 门不可达。
- **实修取证** (TEMP sim-probe, sprint seed7 50k 全程 sites 恒 10 → 挖出放量层
  三缺陷 + 采集面一缺陷, 与原判「放量与定编不联动」不同):
  1. **core-depot 占位容器风暴**: handleCoreDepotSite 在 RCL2 (storage/terminal
     buildMax=0) 走占位分支, 在核心库点位放 5000 能量占位容器×2 且先于 regular
     循环——死积压卡 2 槽位 40k tick, 拆换 (排空→拆→重放) 又是三轮吞吐
     (probe 实锤 c@(34,17)/c@(35,18) = core-depot-placeholder dedupeKey)。
  2. **road 垫底永无预算**: PLACEMENT_ORDER 硬编码 road=8, ext+container 塞满
     10 槽 (maxSitesPerPass) 后 budget=cap-sites=0 → 沼泽房 50k 零道路,
     W1 工人沼泽 fetch 往返 300t+ (move:build=167k:5k, 建造利用率 ~16%)。
  3. **每源容器计数只数建成**: placedContainerPerSource 只查 FIND_STRUCTURES,
     在途工地不挡重复放量。
  4. **采集面 W1 起步**: harvester 最低预算 150 (W1M1), 双源房收入锁死 2/t
     (probe 实锤 H 恒 2×W1, 源能量 2500+ 堆积没人采)。
- **修复**:
  - sitePlacement.ts: PLACEMENT_ORDER 配置化进 PLANNER_CONFIG.placementOrder,
    road (5) 提到 container (6) 前——扩容之后先修命脉路网 (源容器/cc 独立放量
    不经此序); 占位加 coreDepotPlaceholderMinRcl=4 门 (贴起建门槛才占);
    每源容器计数含在途工地。
  - planners.ts + economy.ts: BUILD_COMPLETION_CONFIG 近完提权——工地进度
    ≥60% 时任务 +20 分收尾 (收尾一个 ext 立即解锁 cap+50, 防摊开施工)。
  - rushBodies.ts + rush.ts: RUSH_HARVESTER_MIN_BUDGET 150→250 (W2M1 起步,
    单源收入 4/t; 双实现同步改防口径分裂)。
  - 附带清理: buildMinLevels 死配置删除 (roadMinRcl 直接接线 getLayoutPointsForRcl)。
- **修复效果** (sprint 50k): sites 全程 ≤8 且 **t47500 清零** (修复前 50k 后仍
  恒 10 积压); prog@40000 16536→19311 (+17%)。
  正向外溢: boot L3@15764 / speedrun L3@21349 **新达成** (基线均无 L3),
  race L2@796。
- **遗留** (P1-14 沼泽低均衡深水区, 备注维持不单独勾销口径): sprint L4@40000
  未达 (差 ~25k 进度)——W2M1 后采集面爬升仍慢 (Hwork 2→7 需 30k), 能量水位
  与换代节拍耦合是 P1-14 主战场。
