# TaskBoard 任务 id 生日碰撞——同 tick 批量建任务静默覆盖

- 优先级: P2
- 发现日期: 2026-10-17
- 状态: 已修复 (nexus-architecture-refactor 任务 5.3 单测暴露)
- 来源: TaskIndex 单测 (tests/task-index.test.ts) 「分配扫描成本与任务总量解耦」——
  大表 (1020 任务) 播种后 list 返回 19/20, 丢 1 条。

## 现象

`newTaskId` = `t{tick.toString(36)}{16bit 随机}`。同 tick 批量建任务时 (经济 planner
每 tick 逐房刷新), 16bit 空间的生日碰撞使两个任务拿到同一 id:

```ts
tasks[task.id] = task;   // 后者静默覆盖前者
```

被覆盖任务从记录表消失, 但其 dedupeKey 已被前一次 upsert 消费——本 tick 内该意图
任务直接丢失 (生产端下一刷新周期才会重建)。索引化后覆盖还会使桶内残留双重引用。

## 概率

- 同 tick 建 n 任务碰撞概率 ≈ n(n-1)/2^17。
- n=30 (多房刷新) ≈ 0.7%/tick; 长跑 (50k tick) 几乎必然多次发生。
- speedrun 复核实测: 修复后 L3 21113→21005 (-108t), 即碰撞丢失在冲级场景真实发生。

## 修复

碰撞不改用重掷 (会消耗确定性随机流, 移位后续所有随机决策), 改递增后缀:

```ts
let id = `t{tick36}{rand16}`;
if (碰撞) id = `${id}~${n}`;   // n 递增至空位
```

## 验证

- 单测 5/5 绿 (大表播种不再丢任务; 1020 任务同 tick 播种必碰撞, 确定性复现)。
- 生产线口径: 同 tick 新建任务通常 ≤5 条, 单次碰撞概率 ~0.02%/tick——低频但
  长跑必然发生, 属静默数据丢失类缺陷 (无告警、无日志)。
- 时间线中立: 修复 (后缀版, 不消耗随机流) 后全场景 RCL 读数与修复前 bit 一致
  (speedrun L3@21113 等); 中间版「碰撞重掷」曾致 speedrun -108t, 系额外消耗
  Math.random 移位随机流 + 碰撞任务立即可用 (前置版下一 tick 才重建) 的复合
  效应, 已废弃。
