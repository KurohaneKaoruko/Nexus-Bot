## P0-1 没有 extension 建造逻辑 → 能量容量永久锁死 300

**状态**: ✅ 已修复 (2026-10-11)
- construction.ts 新增 extension 规划: 按 `CONSTRUCTION_CONFIG.extensionMaxByRcl` 缺口在 spawn 周围 2..4 环带落位 (排除墙/占用/工作位/容器位/controller 周边), 每 tick 至多 2 站点;
- 主干道 (spawn↔controller↔sources) 在 extension 落位后低频 (150t) findPath 铺路 (顺带修 P2-9);
- Source 容器逻辑不变, 不被 extension 阻塞。
- **sim 回归**: boot 20k —— 建造能量 10000 → 28900 (5×ext 15000 + 容器 10000 + 道路 3900), RCL2 容量 550 断言 3/3 PASS。

**现象**: `energyCapacityAvailable` 全程 300; 建造能量 10000 全部是 source 容器; `grep extension src/modules/economy/construction.ts src/config/economy.ts` 零命中。

**根因**: construction.ts 只实现了 docs/nexus-design/17 的"Source 容器最小闭环", RCL 解锁 extension 后无人规划建造。

**后果链**: 容量 300 → 所有角色只能买 3 部件身体 (harvester [work,move]×2 恰好 300, upgrader/universal [w,c,m]×1) → 采集/升级/搬运产能天花板, 后面所有优化都被这层封死。

**修复** (src/modules/economy/construction.ts):
1. RCL ≥2 时按 `CONTROLLER_STRUCTURES.extension[rcl] - 现有数` 规划 extension 站点, 沿用现有 `containerSpot` 的选址模式 (spawn 周围安全格, docs/nexus-design/17 布局);
2. 同一模块顺带把 spawn→controller→source 的主干道 road 纳入规划 (修 P2-9);
3. 失败冷却与现有 worksite 机制一致 (siteRetryAt)。

**验证**: `sim/target/release/nexus-sim -s sim/scenarios/boot-from-scratch.json -b dist/main.js` 跑 20k, 观察报告中建造能量 >30000、energyAvailable 上限随 RCL 增长。

**预期收益**: upgrader 可上 4 段以上身体 → 升级吞吐 5-10 倍。

## P0-2 upgrade 任务能力要求缺 carry → ERR_FULL 失败循环 → 升级停摆 → RCL 降级

**状态**: ✅ 已修复 (2026-10-11)
- planners.ts upgrade `requiredCapabilities` → `["work","carry","move"]`;
- agents/index.ts onReplan 分级: `carry-empty`/`site-gone`/`store-empty` 等瞬态原因只 release 回池, 不再 `board.fail` 计数。
- **sim 回归**: boot 20k —— 升级 765 → 8829, RCL 时间线 `L1@0 L2@650` 无降级, 断言 3/3 PASS, 零错误。

**现象** (t1600 任务快照): `upgrade | failed | attempts: 5 | reason: -8`; 失败时持有者是 harvester `H-4457`。全程 upgrade 意图仅 765 次且集中在开局。

**根因链**:
1. planners.ts:87 upgrade 任务 `requiredCapabilities: ["work", "move"]` —— [work,move] 无 carry 的 harvester 合格;
2. allocator 把 upgrade 分给空闲 harvester (upgrader 存活间隙被抢占);
3. agentSystem `fetchEnergy`: 容器大多为空 (见 P0-3) → 命中矿工落地堆 → `pickup`;
4. shim/engine: 无 carry → `getFreeCapacity()=0` → pickup 返回 **ERR_FULL(-8)** → broker 归类 replan;
5. agents/index.ts:19 `onReplan → board.fail` 计一次 attempt; 5 次后任务 **failed**, 100t 冷却 → 重建 → 又被 harvester 抢 → 循环;
6. 升级长期停摆 → RCL2 的 10000t 降级计时到期 → **降回 RCL1** (10 万 tick soak 实锤)。

**修复** (两处, 建议都做):
1. planners.ts:87 改 `requiredCapabilities: ["work", "carry", "move"]` (upgrader 身体 [w,c,m] 满足);
2. agents/index.ts onReplan 区分瞬态与真失败: `carry-empty` / `target-full` / `site-gone` 这类 broker 注释里明确"视为成功路径"的 reason 不应 `board.fail` 累计 attempts, 只 release 任务让对账决定 (actionBroker.ts:176 自己写着"任务完成由对账确认", 但 onReplan 无差别 fail, 自相矛盾);
3. 可选加固: board.fail 的 attempts 上限按 kind 区分 (upgrade 这种常驻任务 5 次太苛刻)。

**验证**: 修后 20k 场景 `rclReachedBy value 3` 应在 20k 内达成 (配合 P0-1); `--dump-memory` 中 upgrade 任务不再出现 `reason: -8`。

## P0-3 矿工驻点在容器旁边而非容器上 → 采集能量全部绕过容器落地

**状态**: ✅ 已修复 (2026-10-11, 单测覆盖; **sim 回归待跑**)

**修复** (src/modules/world/worksite.ts):
1. `containerSpotFor` 直接返回驻点本身 —— 驻点与容器位合一, 矿工站容器上采矿;
2. 新增 `PASSABLE_SITE_TYPES`(road/container): `walkableAdjacents` 与 `worksiteValid` 只把**不可通行**工地视为占用, 容器工地建在驻点上不再使驻点失效 (修选址漂移);
3. 驻点评分新增容器亲和加成 `WORKSITE_CONFIG.containerAffinityBonus`: 已有容器 (结构/工地) 的相邻格优先, 替补无缝继承既有容器位;
4. `WorksiteRecord.containerSpot` 语义更新为「= 驻点」(schema 注释同步), construction.ts 落站点逻辑不变 (天然建在驻点下);
5. agentSystem 的满载卸货路径不变: `containerSpot` 与驻点同格 → 距离 0 ≤ RANGE_ADJACENT → transfer 成立。

**验证** (单测): `tests/world/worksite.test.ts` —— 容器期望位与驻点同格 / 容器工地不使驻点失效 / 不可通行工地 (extension) 仍触发重选 / 已有容器时驻点优先落在容器格; `tests/agents` 18 例无回归。
**待办**: 按原验证标准跑 `boot-from-scratch` 20k —— 观察 pickup 意图骤降、withdraw 上升、容器存量稳定高位、`--dump-memory` 中 worksite 与 containerSpot 坐标一致。

**现象**: 采集 131k, pickup 仅 477; 容器长期空转; 诊断持续 `transport`、carrierMultiplier 顶格。

**根因**: worksite.ts:67 `containerSpotFor` 明确选"**驻点以外**的相邻格"（注释"与驻点不同格"），矿工钉在 (19,21) 而容器在 (19,22)。矿工无 carry，挖出的每一焦耳经 drop_overflow 落在自己脚下成堆，容器完全接不到货。

**设计意图 (定案)**: 矿工**站在容器上**采矿——溢出/落地能量经官方 `_create-energy` 机制直接流入同格容器（sim 已实现并有回归测试 `dropped_energy_fills_container_first` 锁定）。无需给矿工加 carry，carrier 从容器 withdraw 即可，落地堆只剩容器满时的溢出兜底。

**已验证的正反馈**: sim 补上"掉落入容器"机制后（墓碑散落/溢出在容器格的能量开始入容器），仅此一条就令升级吞吐 765 → 16641 (20×)，upgrade 任务不再出现 ERR_FULL 失败循环——证明容器货源就是升级链路的命门，驻点合一后收益会完全兑现。
