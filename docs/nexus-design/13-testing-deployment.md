# 13. 测试、模拟、部署与可观测性

## 13.1 构建与部署

推荐 TypeScript 工程搭配 Screeps API 类型定义和 Bundler。社区维护的 [screepers/screeps-typescript-starter](https://github.com/screepers/screeps-typescript-starter) 可用于基础编译和上传流程；本文的 Nexus 模块是需要自行实现的业务层。

建议把部署目标显式区分：

- `sim`：本地/浏览器模拟，适合快速重现基础行为；
- `test`：独立测试分支或私服，用于集成与长时间稳定性；
- `main`：实际长期运行的目标分支。

凭据、私服地址和上传 Token 应保存在开发者本地环境，不要提交至 Git。

## 13.2 测试金字塔

### 单元测试

优先测试纯函数：任务评分、身体成本计算、房间收益评分、Memory 迁移、资源预留、路线 key、任务状态转移与生产配方依赖。

### 模块测试

用模拟对象验证：TaskBoard 租约过期、Allocator 能力筛选、SpawnDirector 队列选择、经济账本的预留与结算、ActionBroker 对无效目标的处理。

### 场景测试

在模拟/测试房间测试：

- 从零到基础稳定经济；
- 能源不足时生产降级；
- 采集目标被移除；
- Creep 死亡后任务回收；
- 路口拥堵与不可达路线；
- 敌人出现导致防御抢占普通任务；
- 远程采集收益低于阈值时退出；
- 房间失去视野后 Intel 过期；
- Terminal/市场的资源成本与库存预留；
- Memory schema 升级和异常恢复。

### 长时间 soak test

持续运行数千 Tick，关注 Memory 增长、任务抖动、CPU 趋势、孤儿任务、生产失衡、缺货和日志重复。很多 Screeps Bug 不在单个 Tick 暴露，而是长期状态累积造成。

## 13.3 回归基准

每次大改之后，在相同地图/相同初始条件下记录：

- RCL 进展速度；
- Energy 可用储备和净产出；
- Source 利用率；
- Spawn 闲置时间；
- 单位生产数、死亡率与任务完成率；
- 远程采集净收益；
- 平均/高分位 CPU；
- Memory 大小；
- 敌人造成的结构损失与恢复时间。

不要只根据“看起来单位更多”判断改进。更多 Creep 可能降低吞吐效率并提高 CPU 成本。

**核心不变量** (docs/nexus-design/23 §12.4, 回归时逐条核对):
① 单单位单租约 ② 同 actor 同方法每 tick 一次 ③ 正常不覆盖紧急锁定提交 ④ 提交 ≠ 完成
⑤ 持久引用可失效可重建 ⑥ 资源不被重复消费 ⑦ 等待必有超时/解除 ⑧ 高成本任务可跳过/分片/延后
⑨ 每殖民地有最低生存计划与不可自救判定 ⑩ 战略动作可追溯目标/预算/授权。

**场景测试表** (docs/nexus-design/23 §12.2, sim 场景按此扩充): 开局闭环 / 矿工集体退休 /
运输堵塞 / 取货点被拆 / 卸货点满载 / 失视房间 / CPU 不足 / global reset / 旧 Memory 迁移 /
敌军突袭 / 集群失主房 / (跨 shard 幂等——跨 shard 阶段补)。
sim 回放不能证明服务器结算一致, 引擎级集成 (sim 真实 bundle) 才算通过。

## 13.4 可观测性

推荐使用 `RoomVisual` 和限频日志显示：

- 房间战略姿态与风险级别；
- Source/Container/关键物流节点；
- 任务 ID、状态、租约剩余时间；
- 拥堵点和路径缓存状态；
- Spawn 队列及关键能力缺口；
- CPU 本 Tick 与 Bucket 趋势；
- 关键经济指标和扩张候选分数。

可视化应该有开关与采样周期，正式环境不要默认绘制所有细节。

## 13.5 发布策略

1. 每次只引入一个主要子系统。
2. 先在模拟环境跑场景测试。
3. 在测试分支长时间运行并检查指标。
4. 合并后监控 CPU、Memory、错误率和关键经济指标。
5. 出现异常时能快速回滚到最近的稳定 bundle。

Screeps Bot 的版本回退与 Memory schema 兼容要一起考虑：新代码读取旧 Memory 时必须能迁移或安全降级。仅仅把代码回滚、却把 Memory 留在不兼容的新格式，也可能造成第二次故障。
